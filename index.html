Setting Up OWASP Juice Shop

OWASP Juice Shop is an intentionally vulnerable Node.js / Express / Angular application covering the entire OWASP Top 10 and more. This guide is aligned to the OWASP Top 10:2025 and presents one flagship exercise per category (10 issues total). Steps verified against Juice Shop v20.0.0 (May 2026) — requires Node.js 22–25 or Docker.

🐳 Quick Start — Docker

  • Pull the Juice Shop image
    docker pull bkimminich/juice-shop:v20.0.0
  • Run the container
    docker run -d --name juiceshop -p 3000:3000 bkimminich/juice-shop:v20.0.0
  • Open in your browser once you see "Server listening on port 3000": http://localhost:3000
  • Reset a clean instance
    docker stop juiceshop && docker rm juiceshop

🔧 Recommended Tools

  • Browser DevTools (F12) — Network, Application, Console tabs
  • Burp Suite Community / OWASP ZAP — intercept and modify HTTP requests
  • curl / Postman — direct API testing  ·  jwt.io — decode JWT tokens
  • CrackStation — hash-cracking demos
⚠
Lab ethics: Only use these techniques on systems you own or have explicit written permission to test. Juice Shop is intentionally vulnerable — never run it exposed to the public internet or a shared network.

🔒 A01:2025

Broken Access Control

The #1 web application risk. Access control enforces policy so users cannot act outside their intended permissions. Broken controls allow attackers to view other users' data, access admin functions, or bypass authentication entirely. In 2025, SSRF is now absorbed into this category.

Critical prevalenceIDORPrivilege escalationSSRF (absorbed 2025)
💡
Why this issue: Chosen as the flagship issue: IDOR is the single most common real-world manifestation of broken access control and chains directly into data-breach scenarios.
Flagship Exercise (1 of 1)
01
IDOR — View and modify another user's shopping basket ✓ Verified v20
Easy ▼
  • Register a new account and log in. Add any item to your cart.
  • Open DevTools (F12) → Network tab. Click Your Basket in the top navigation.
  • Find the API request to /rest/basket/<id> and note your own basket ID (e.g. 6).
  • Request a different basket ID directly using your JWT (DevTools → Application → Local Storage → token):
    curl -s http://localhost:3000/rest/basket/1 \ -H "Authorization: Bearer YOUR_TOKEN" | python3 -m json.tool
  • Try IDs 1, 2, 3… each returns a different customer's basket.
  • Bonus: add an item to another user's basket via PUT /api/BasketItems with a different BasketId.
Expected result
✅
You can view (and modify) any user's basket contents simply by changing the numeric ID. This is a classic Insecure Direct Object Reference — the server never checks whether the basket belongs to the requesting user.
💡
Remediation: Validate server-side that the requested resource belongs to the authenticated user. Use opaque, non-sequential identifiers (UUIDs) so object references cannot be guessed or enumerated.
⚙ A02:2025

Security Misconfiguration

Jumped from #5 to #2 in 2025 — now the second most critical risk. Covers improperly configured permissions, unnecessary features, default accounts, verbose errors, and missing hardening. Every tested application in the 2025 dataset showed at least one misconfiguration.

Universal prevalenceDirectory listingDefault credentialsMissing headers
💡
Why this issue: Chosen as the flagship issue: the exposed FTP directory plus the null-byte filter bypass is the canonical Juice Shop misconfiguration and demonstrates two distinct failures at once.
Flagship Exercise (1 of 1)
01
Browse the exposed FTP directory and bypass the file-extension filter ✓ Verified v20
Easy ▼
  • Navigate directly to the exposed FTP directory:
    http://localhost:3000/ftp
  • Observe the full directory listing. Download acquisitions.md — confidential fictional M&A data that should never be public.
  • Try to download coupons_2013.md.bak — the server blocks .bak files. Bypass the filter with a null-byte injection:
    http://localhost:3000/ftp/coupons_2013.md.bak%2500.md
  • Also download package.json.bak — used later in the A03 Supply Chain exercise.
  • Check response headers in DevTools → Network for missing X-Frame-Options, Content-Security-Policy, X-Content-Type-Options.
Expected result
✅
Sensitive files are browsable by anyone. The null-byte trick defeats the server's extension allowlist by terminating the string early at the C-level \0 character. Multiple security headers are missing.
💡
Remediation: Disable directory listing. Remove all non-production paths from web roots. Use allowlist extension filtering based on magic bytes (file content), not the file name. Enable all OWASP-recommended security headers.
📦 A03:2025

Software Supply Chain Failures

Brand-new category in 2025, evolved from "Vulnerable and Outdated Components." Scope is now much broader — beyond known CVEs to dependency confusion, typosquatting, compromised build pipelines, and open-source package poisoning.

Known CVEsDependency confusionOutdated librariesExposed manifests
💡
Why this issue: Chosen as the flagship issue: retrieving and analysing the exposed manifest is the foundational supply-chain task that every other supply-chain attack builds on.
Flagship Exercise (1 of 1)
01
Retrieve and analyse the exposed package manifest from FTP ✓ Verified v20
Easy ▼
  • Download the backup package manifest from the FTP directory (use the null-byte bypass from A02):
    http://localhost:3000/ftp/package.json.bak%2500.md
  • Examine the dependencies and devDependencies sections. List every dependency name and its exact pinned version.
  • For each key library, search the National Vulnerability Database (nvd.nist.gov) and Snyk (security.snyk.io).
  • Document: how many CVEs exist for the exact versions shown? What is the highest CVSS score?
Expected result
✅
Full dependency list exposed. Multiple libraries have published CVEs for the exact versions in use — an attacker now has a targeted attack roadmap of known working exploits.
💡
Remediation: Never expose package manifests. Maintain a private SBOM instead. Run npm audit, Snyk, or Dependabot in CI/CD and block deployments that contain critical CVEs.
🔑 A04:2025

Cryptographic Failures

Dropped from #2 to #4, reflecting improved TLS adoption and stronger default ciphers, but still critical. Covers weak or absent cryptography — broken hashing (MD5, SHA1), cleartext storage or transit, insecure randomness, and poor key management.

Weak hashingSensitive data exposureCleartext storage
💡
Why this issue: Chosen as the flagship issue: cracking the unsalted MD5 admin hash is the clearest demonstration of a cryptographic failure leading directly to full account compromise.
Flagship Exercise (1 of 1)
01
Crack MD5 password hashes retrieved from the exposed Users API ✓ Verified v20
Medium ▼
  • Retrieve the admin user's record from the API (works while logged in as any user):
    curl -s http://localhost:3000/api/Users/1 \ -H "Authorization: Bearer YOUR_TOKEN" | python3 -m json.tool
  • Copy value of your jwt token available in dev tool. Decode using jwt.io
  • Paste the pash hash into https://crackstation.net — the rainbow-table lookup instantly returns the plaintext.
  • Alternatively crack locally with hashcat:
    hashcat -m 0 hash.txt /usr/share/wordlists/rockyou.txt
  • Discuss: MD5 has no salt and is trivial to reverse. The admin hash cracks in milliseconds.
Expected result
✅
MD5 hash reversed instantly — admin123 revealed. The entire password database is compromised the moment any storage flaw exposes the hashes.
💡
Remediation: Use bcrypt (cost 12+), Argon2id, or scrypt for password hashing. These are slow by design and salted per user, making rainbow tables and brute force infeasible. Never use MD5, SHA1, or SHA-256 alone for passwords.
📈 A05:2025

Injection

Moved from #3 to #5, indicating improved awareness and tooling, but still highly dangerous. Includes SQL, NoSQL, OS command, LDAP injection, and Cross-Site Scripting. Untrusted data tricks an interpreter into executing unintended commands.

SQL injectionAuth bypassXSS
💡
Why this issue: Chosen as the flagship issue: SQL injection login bypass is the textbook injection attack and the most impactful single-step compromise in the application.
Flagship Exercise (1 of 1)
01
SQL injection — bypass login and authenticate as admin ✓ Verified v20
Easy ▼
  • Go to the login page: http://localhost:3000/#/login
  • In the Email field, enter the SQL injection payload:
    ' OR 1=1--
  • In the Password field, enter anything (e.g. x). Click Log In.
  • The backend query becomes the following. The trailing comment neutralises the password check and the always-true condition returns the first row (admin):
    SELECT * FROM Users WHERE email='' OR 1=1--' AND password='...'
  • Verify you are now logged in as admin@juice-sh.op.
Expected result
✅
Authenticated as admin with no valid credentials. The SQL comment neutralises password validation entirely.
💡
Remediation: Use parameterized queries (prepared statements) — never concatenate user input into SQL strings. With a parameterized query, ' OR 1=1-- is treated as a literal string, not executable SQL.
🌟 A06:2025

Insecure Design

Missing or ineffective security controls baked into the design — not implementation bugs. Business-logic flaws, missing abuse-case thinking, no rate limiting, and trust-model failures. 2025 expands this to AI-integrated attack surfaces including prompt injection.

Business logicNo rate limitingAI prompt injection (2025)
💡
Why this issue: Chosen as the flagship issue: the negative-price order is the definitive business-logic / insecure-design flaw with direct financial-fraud impact.
Flagship Exercise (1 of 1)
01
Business logic — order products at a negative price ✓ Verified v20
Medium ▼
  • Log in and add any item to your cart. Open DevTools → Network.
  • Click the + / - quantity buttons on the cart page. Find the PUT /api/BasketItems/<id> request.
  • Open Burp Suite, intercept the PUT request, and change the quantity value to a negative number:
    {"quantity": -100}
  • OR Use curl if you don't have BurpSuite curl -X PUT "http://localhost:3000/api/BasketItems/1" -H "Authorization: Bearer " -H "Content-Type: application/json" --data '{"quantity":-100}'
  • Forward the request. The cart total now shows a large negative value.
  • Proceed to checkout — the order can still be placed. Discuss the financial-fraud implications.
Expected result
✅
Order placed at a negative total — the server performs no range validation on quantity. A design flaw: the application was never designed to handle this abuse case.
💡
Remediation: Validate all numeric inputs server-side with explicit range constraints. Conduct threat modeling and abuse-case analysis during design. Never trust client-provided values in financial calculations.
👤 A07:2025

Authentication Failures

Renamed from "Identification and Authentication Failures" — now focused purely on authentication weaknesses: weak passwords, missing brute-force protection, insecure recovery flows, poor session management, and JWT vulnerabilities.

Weak password resetBrute forceJWT attacks
💡
Why this issue: Chosen as the flagship issue: the weak security-question password reset is the most realistic authentication failure and demonstrates a complete account takeover with no credentials.
Flagship Exercise (1 of 1)
01
Reset the account account password via a weak security question ✓ Verified v20
Medium ▼
  • Go to the Forgot Password page: http://localhost:3000/#/forgot-password
  • Enter the bjoern email bjoern@owasp.org — the security question appears: "Name of your favorite pet?"
  • Find Bjoern’s Twitter post at https://twitter.com/bkimminich/status/1594985736650035202 and check his post.
  • Once accepted, set a new password and log in as admin. Note: no email verification, no OTP — just a guessable answer.
  • Also try resetting bender@juice-sh.op (hint: the answer is Stop'n'Drop).
Expected result
✅
Admin password reset without any email verification — purely by guessing a knowledge-based answer. No authentication of the "forgot password" requestor is performed.
💡
Remediation: Eliminate knowledge-based security questions entirely. Replace with email OTP or TOTP MFA. Rate-limit and log all reset attempts. Consider passwordless auth (passkeys) per 2025 best practice.
📄 A08:2025

Software or Data Integrity Failures

Code and infrastructure that does not protect against integrity violations. The 2025 version explicitly includes CI/CD pipeline attacks, insecure deserialization, unsigned updates, and JWT algorithm confusion.

Malicious uploadsJWT tamperingCI/CD pipeline attacks (2025)
💡
Why this issue: Chosen as the flagship issue: the disguised malicious upload is the clearest data-integrity failure — the server trusts client-declared content instead of verifying it.
Flagship Exercise (1 of 1)
01
Upload a disguised malicious file via the complaint form ✓ Verified v20
Medium ▼
  • Log in and navigate to the complaint form: http://localhost:3000/#/complain
  • Create a test file named malware.js with content alert('pwned'). The UI rejects non-PDF/ZIP files.
  • Open Burp Suite and intercept the file upload. Change Content-Type from application/javascript to application/pdf and the filename to totally-legitimate.pdf.
  • Forward the modified request, then verify the file was accepted:
    docker exec juiceshop ls /juice-shop/uploads/complaints/
  • Try accessing the uploaded file via its predictable path. Discuss execution risk if the directory is served.
Expected result
✅
Non-PDF file accepted by changing the MIME type — the server validates the client-declared Content-Type, not the actual file content (magic bytes). The file is stored in a predictable location.
💡
Remediation: Validate file content using magic bytes (libmagic), not client MIME headers. Generate random filenames, store uploads outside the web root, scan on upload, and serve from a separate no-execution domain.
👁 A09:2025

Security Logging and Alerting Failures

Renamed from "Security Logging and Monitoring Failures" — 2025 emphasises alerting as the critical gap. Without timely alerts, breaches go undetected for months. Covers insufficient logging, missing real-time alerting, exposed logs, and log injection.

No detectionMissing audit trailNo alerting on attacks
💡
Why this issue: Chosen as the flagship issue: unrestricted brute force with no lockout and no alerting is the most direct demonstration that attacks go entirely undetected.
Flagship Exercise (1 of 1)
01
Brute-force the login — no rate limiting, no lockout, no alerts ✓ Verified v20
Easy ▼
  • Run 20 consecutive failed login attempts against the admin account:
    for i in $(seq 1 20); do STATUS=$(curl -s -o /dev/null -w "%{http_code}" \ -X POST http://localhost:3000/rest/user/login \ -H "Content-Type: application/json" \ -d "{\"email\":\"admin@juice-sh.op\",\"password\":\"wrong${i}\"}") echo "Attempt $i: HTTP $STATUS" done
  • Observe: no rate limiting, no CAPTCHA, no account lockout — every request gets the same response speed.
  • Check the /support/logs endpoint — are these 20 attempts recorded? Is any alert triggered?
  • Discuss: with no lockout, a common-password list plus a known email yields a successful login in minutes.
Expected result
✅
20+ failed logins with no lockout, no CAPTCHA, no rate limiting, and no alerting. A brute-force attack would go entirely undetected until the attacker succeeds.
💡
Remediation: Implement progressive delays (exponential backoff) after failed logins. Lock accounts after N failures with email unlock. Add CAPTCHA after 3–5 failures. Set up real-time alerts and log every attempt with IP, timestamp, and user agent.
⚠ A10:2025

Mishandling of Exceptional Conditions

Entirely new category in 2025. Addresses failures in how applications handle abnormal inputs, unexpected states, and errors. Poor exception handling leads to crashes, "failing open," information disclosure via stack traces, and denial of service.

Failing openStack trace exposureNull byte injection
💡
Why this issue: Chosen as the flagship issue: the null-byte "fail open" ties the new category back to a concrete, observable exploit and explains the underlying cross-language string-handling exception.
Flagship Exercise (1 of 1)
01
Trigger "fail open" via null-byte injection and malformed input ✓ Verified v20
Medium ▼
  • Revisit the FTP null-byte bypass and understand why it works:
    http://localhost:3000/ftp/coupons_2013.md.bak%2500.md
  • The server's extension check sees the name ending in .md (after %00). The OS layer reads coupons_2013.md.bak\0.md and stops at \0 — accessing the .bak file. A classic cross-language string-handling exception.
  • Probe other inputs for exceptional-condition handling — send an unexpected data type to the search API:
    curl -s "http://localhost:3000/rest/products/search?q[]=array"
  • Send an oversized payload to test DoS-style exception handling and observe whether the app crashes, returns a 500 with a stack trace, or fails gracefully.
Expected result
✅
The null-byte attack exploits a mishandling of exceptional conditions between the JavaScript string check and the OS file-system call. Array/oversized inputs may cause unhandled exceptions and verbose error responses that expose internal state.
💡
Remediation: Define explicit types and ranges for all input parameters. Handle exceptions "fail closed" — when in doubt, deny. Validate at the boundary with allowlists. Never expose exception details. Set payload size limits in the framework and reverse proxy.
